### Slide 05 · 技术栈（20 秒）

> 【**Ziqing Ji**】

技术栈全部 Python 生态。两个关键决策：

第一，**所有金融运算用 Decimal 28 位精度**，不用 float——避免浮点误差累积。第二，**链上数据接入只用标准库 urllib**，不引入新依赖。这意味着助教离线环境里只要拷一份 cache 就能跑。

测试与 CI 用 `pytest + hypothesis + pytest-cov + pytest-benchmark` 四件套加上 GitHub Actions，三个 Python 版本矩阵跑全套测试。

---

### Slide 06 · 5 层架构（30 秒）

> 【**Ziqing Ji**】

架构是清晰的 5 层模块化。从下往上：

- 最底层 `data_model` 是不可变值对象 + 数据加载
- 往上 `strategy` 是策略引擎，包含 6 个评分器、轮动引擎、复投引擎
- 再往上 `backtest` 是回测主循环，含 Mark-to-Market 和摩擦成本估算
- 然后 `report` 是绩效与归因
- 最顶层 `ui` 是 Streamlit 看板

**依赖严格自上而下，下层不感知上层**。每层之间通过抽象接口对接，比如 `IScorer`、`IFrictionEstimator`——任何一个 Scorer 都可以热插拔替换。

右侧四个设计原则：frozen dataclass 保证不可变、Decimal 保证精度、抽象接口保证可扩展、MappingProxyType 保证值对象真正不可变。

### Slide 07 · 端到端数据流（25 秒）

> 【**Ziqing Ji**】

每个 tick 严格执行 8 步：事件注入 → MTM 重估 → 收益累计 → 评分 → 复投 → 轮动 → 写日志。

重点看右侧的**关键创新 Mark-to-Market**——每个 tick 按 token price 的变化比例重估持仓。

**性能方面**：365 tick × 3 池只要 0.19 秒，1000 tick × 5 池 0.75 秒，远低于 5 秒的预算上限。

### Slide 12 · 守恒等式（25 秒）

> 【**Jingcheng Wang**】

数学严谨性方面，我们做了一件特别的事——**用集成测试守恒等式来验证归因正确性**。

公式很简洁：**理论收益 = 实际收益 + Gas + Slippage + LVR + 调仓空窗折损**。

下面 4 个卡片是每一项的具体公式，比如 LVR 用了 `|oracle - pool| / oracle × size × 0.5`。

底部是验证代码：`abs(reconstructed - theoretical) <= Decimal(1)`——**误差小于 1 元，对 10 万本金来说就是 0.001%**。这个断言在每次跑集成测试时都会被验证。

### Q&A 可能被问的 5 个问题

**Q1：你最自豪的是什么？**
> A：属性测试自动发现的那个边界 bug（BUG-004）。`sample_data` 在 `n_days < crash_window` 时切片越界，是 hypothesis 用随机种子穷举发现的——人写测试时绝对想不到这个情况。这证明了我们对测试方法学不是死记。

**Q2：MTM 修复前 Sharpe 1198 是怎么发现的？**
> A：端到端测试跑完后我们看 metrics 报表，Sharpe 1198 一眼就不正常。回头看代码才发现 NAV 没有按价格重估。这是「测试驱动找到设计缺陷」的实例。

**Q3：为什么用 Decimal 不用 float？**
> A：浮点累积误差会让守恒等式断言失败。我们做过实验，相同种子两次跑 float 得到的 NAV 序列会在第 100 个 tick 之后出现 1e-12 的偏差，不能严格复现 NFR-02。

**Q4：测试覆盖率 87.5% 没到 100% 是什么没测？**
> A：主要是 `onchain_fetcher.py` 真实 HTTP 路径，覆盖率只有 68%。单元测试用 mock 替代真实网络，真实路径只能靠手测。这是有意识的取舍。

**Q5：为什么选 Streamlit 不选 React/Vue？**
> A：项目核心是策略验证而不是 UI 创新。Streamlit 让我们用 Python 直接写界面，**和后端共享 Decimal 类型不需要序列化**，并且 hot reload 极大提升迭代效率——一周内做完 6 Tab × 10 图表。
